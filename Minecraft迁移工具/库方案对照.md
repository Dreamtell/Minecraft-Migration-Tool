## 2. 逐个看

### 2.1 `tksheet` 替 `VirtualTable` —— 做过并排 demo，**实测结论：不换**

- 现状：自绘 Canvas 表格 510 行，自己管可见行、槽位复用、排序、悬停、水平滚动、平滑滚动。
- 库：[tksheet](https://pypi.org/project/tksheet/) 7.6.0，MIT、2.5 MB、零依赖。
- 并排 demo（同一份 500 行数据、都用深色主题，截图 `表格对比demo.png`）实测：

| 项目 | 旧：VirtualTable | 新：tksheet 7.6.0 |
|---|---|---|
| 构建 500 行 | 590 ms | **301 ms**（快一倍） |
| 滚轮一格 | 平滑动画，7 帧 / 132 ms，单帧重绘 **0.03~4 ms** | **一次跳到位**（无动画），单次重绘 **23~38 ms**（800 行与 2000 行都是 ~24 ms） |
| 附带功能 | 无 | 行号列、列宽拖拽、点表头排序、复制、查找、单元格编辑、下拉 |
| 配色 | 就是我们的主题（含 ✅/❌/⚠️ tag 色） | 它自带深色主题，另一套色板；要贴合得逐项喂色 |
| 已接好的东西 | 主题同步、悬停提示、拖拽 .jar、勾选语义、平滑滚动 | 全都要重写 |

- **否决理由**：滚动重绘贵 6~10 倍（24 ms vs 4 ms）。我们刚做完的平滑滚动是"每帧插值"的，单帧 24 ms 已经超过 60fps 预算（16.7 ms），换上去等于**用卡顿换少写 510 行**——而这 510 行的功能已经全都接好了。
- 什么情况下值得回头再考虑：如果哪天要**单元格编辑、列宽拖拽、搜索、多列排序**这些它白送的功能，那时可以把"放弃平滑滚动"当作可接受的代价。
- 待验证（本机网络受限，pip 拿不到包）：PyInstaller 是否需要 `--add-data`。

### 2.2 `pystray` 替手写托盘 —— 可换，注意许可

已在本机**验真**（它已经装在环境里）：

```
版本 0.19.5   许可 LGPLv3   安装体积 257 KB / 35 文件
依赖 Pillow + six（+ 各平台各自的包）
Icon 方法：run / run_detached / notify / update_menu / stop
MenuItem(text, action, checked, radio, default, visible, enabled)   ← 勾选项、单选、左键默认动作都支持
后端：pystray/_win32.py
```

- 它能覆盖我们现在手写的：勾选式菜单项（"关闭时收进托盘"）、左键打开主界面、气泡通知。
- **它不覆盖**：再次双击 exe 时唤起已有实例、把窗口从托盘叫回来——那套 `RegisterWindowMessage` 逻辑仍要保留（这部分是本项目特有需求，不是托盘的锅）。
- **许可要注意**：LGPLv3 打进 PyInstaller 单文件 exe 属于合规灰区（常见做法是随包附源码或允许替换库）。我们现在的 `pywin32` 方案没有这个问题。

### 2.3 `pywinstyles`（原生暗色标题栏 / 圆角）—— 建议加

- 现状：深色主题下窗口标题栏仍是白色（Tk 不管标题栏）；窗口四角是直角。
- [pywinstyles](https://socket.dev/pypi/package/pywinstyles/overview/1.8) 用 ctypes 调 DWM：暗色标题栏、圆角、亚克力/云母、标题栏配色。
- 纯 ctypes、无数据文件 → PyInstaller 打包基本无风险（对比 sv-ttk 的 `.tcl` 坑）。
- 代价：一处调用（应用主题时给主窗口 + 各 Toplevel 刷一次），几行代码。
- 待验证：Win10 上的降级行为、部分窗口（overrideredirect 的提示框）是否要跳过、许可。

### 2.4 `sv-ttk` / `ttkbootstrap`（ttk 主题）—— 不换

- 它们能把 ttk 控件（Treeview、Entry、Combobox、Scrollbar、Progressbar）一键换成 Win11 风格。
- 但本项目**所有主要控件都是自绘**（53 处渐变按钮、自绘表格、自绘启动卡片），它管不到；剩下那几个 ttk 控件我们已按主题逐个配过。
- 另外 [sv-ttk 有已知 PyInstaller 打包问题](https://github.com/rdbende/Sun-Valley-ttk-theme/issues/86)（`sv.tcl` 要 `--add-data`，否则报 `couldn't read file ...sv_ttk\sv.tcl`）。收益小、坑不少。

### 2.5 `PySide6`（换栈）—— 已做「一个窗口」的试点（见 2.7）

只有它能解决 Tk 架构上做不到的两件事：单控件淡入淡出（`QGraphicsOpacityEffect`）、布局动画（`QPropertyAnimation`）。代价：`ui/` 4000+ 行重写、打包体积 +50~80MB、托盘/通知/拖拽全换实现。等整套视觉改版时一次性做。

### 2.6 `CustomTkinter`（"专门做现代化美化"的那个库）—— 实测后**不换**

问题原话是"为什么就没有专门搞现代化设计美化的库呢"。有，就是它：[CustomTkinter](https://pypi.org/project/customtkinter/)，
MIT，纯 Python，自带深/浅色与多套配色主题。**本次已在本机装上并实测**（pip 的临时目录被沙箱拦了，
改用 urllib 直接下 wheel + zipfile 解包）：

```
customtkinter 6.0.0 wheel 295 KB + darkdetect 0.8.0 9 KB + packaging 127 KB = 431 KB
随包数据文件 8 个：assets/fonts/CustomTkinter_shapes_font.otf、assets/fonts/Roboto/*.ttf、
                  assets/icons/*.ico、assets/themes/*.json（blue/dark-blue/green/gold…）
```

实测数据（同一台机器，本机噪声大，比值比绝对值可信）：

| 项目 | CustomTkinter 6.0.0 | 本项目现状 |
|---|---|---|
| 导入耗时 | **387 ms** | tkinter 约 50 ms |
| 按钮构建 | 4.89 ms/个（12 个 59 ms） | 0.4 ms/个（渐变图缓存命中） |
| 输入框构建 | **14.88 ms/个**（3 个 45 ms） | 0.27 ms/个 + 4 ms 懒出图 |
| 200 行滚动列表构建 | 123 ms（0.62 ms/行，200 个真控件） | 卡片视图按需只画可见 12 行 |
| 滚动一屏 | 2.2 ms 中位 | 9.6 ms/帧（但我们是逐帧插值动画，不是整块跳） |
| 首次绘制（demo 窗口） | 852 ms | 主窗口（大得多）1120–1279 ms |
| 默认字体 | **Roboto**（自带 TTF） | 全程序微软雅黑 |
| 打包 | 8 个 .otf/.ttf/.json 要 `--add-data`（同 sv-ttk 那类坑） | 纯代码 + Pillow，无数据文件 |

**它为什么不是魔法**（这是本题的关键）：实测 `CTkButton` 的子控件是 `[CTkCanvas, Label]` ——
跟我们手写的渐变按钮是同一套路（Canvas 上贴图/画形状 + 文字）；`CTkEntry` 也是 canvas 包一个原生
`Entry`，和我们刚做的 `RoundedEntry` 一模一样。也就是说 Tk 生态里所有"美化库"最后都只能：
**在 Canvas 上自己画像素，再把原生控件嵌进去**。谁来做都绕不开，区别只是封装程度。

根因是 Tk 的三条硬限制：
1. 控件没有 `border-radius`，ttk 的 style 只能替换**预定义绘制元素**，不能定义新形状；
2. 没有"单控件 alpha"和控件级合成，全窗口只有 `-alpha`（还是 layered window，会挡掉系统动画）→ 做不出阴影/毛玻璃；
3. Tk 的核心从 8.6 到 9.0 基本没动过样式层；而 Tk 的用户群是脚本/小工具，没人投钱做设计系统（对比 Qt 有 Qt Company、Flutter/Electron 有大社区）。

**结论：不换。** 换上去的收益是"少写自绘代码"，代价是：
- 现在 4000+ 行 UI（窗口/表格/卡片/动画/主题）全要重写；
- 丢掉已经调好的东西：像素级平滑滚动、卡片视图、自绘表格（CTk 没表格，要另配 tksheet，而 tksheet 滚动 23–38 ms，见 2.1）；
- 丢掉主题统一：它自带一套 JSON 主题 + Roboto 字体，我们这边 130+ 语义色键、几十处引用都对不上；
- 打包多 8 个数据文件、多 431 KB 依赖，外加一个第三方维护节奏（6.0.0 之后更新已明显放慢）。

真要做"整套现代化"，一步到位应该上 **PySide6 + qfluentwidgets**（Windows 11 Fluent 质感、真圆角阴影、QSS 样式表、原生动画），而不是在 Tk 上再包一层。

### 2.7 `PySide6` 试点：只把"放大查看"一个窗口换成 Qt —— **已落地，可随时切回**

新增 `ui/qt_big_view.py`（约 1400 行），与 Tk 版并存：设置 →「放大查看窗口」二选一，
缺 PySide6 时自动回落 Tk 版。两套事件循环同线程共存的做法：Tk 每 12ms 调一次
`QApplication.processEvents()`，Qt 的所有回调都跑在这条 `after` 里，所以主线程/线程安全
与 Tk 一致；Qt 内部线程池用**信号**回传结果，替掉了原来跨线程 `root.after` 那套。

| 项目 | Tk 版放大查看 | PySide6 试点窗口 |
|---|---|---|
| 首次打开 | **501 ms** | 953 ms（冷启动）／之后 **~100 ms** |
| 首次建窗 cProfile | — | 516 ms，其中 `QTableView.setModel` **378 ms**（一次性，第二次建窗 15 ms） |
| 预热是否划算 | — | **不划算**：预热 1231 ms + 打开 102 ms = 1333 ms > 冷开 953 ms，故不做预热 |
| 圆角/阴影 | 手工 PIL 超采样贴图 + 缓存（`_ROUND_CACHE`） | DWM 原生圆角（`DWMWA_WINDOW_CORNER_PREFERENCE=2`）+ 原生窗口阴影 |
| 窗口弹出/关闭动画 | 无（Tk 自绘窗口也不做） | **系统原生**（前提：不能用无边框+半透明，见下） |
| 选中/悬停动画 | 手写 12 帧 `canvas.move` + `after` 定时 | `QVariantAnimation` + 缓动曲线（170ms `OutCubic`） |
| 按钮动画 | 4 帧懒生成补间 + 按下位移 1px | 悬停 190ms `OutBack`（浮起 1.6px + 扫光）+ 按下 90ms 沉、松开 200ms 弹回 |
| 平滑滚动 | 自写 `SmoothScroller`（12ms/帧，每帧 30%，含失控保护） | 同样手感移植到 Qt（`_SmoothWheel`），但**由泵每帧推进一步**，不用 QTimer |
| 排序 | 点表头 → 自写排序 + 指示符 | `QHeaderView` 原生指示符 + 自写排序键 |
| 2000 条整表重载 | 不便对比 | 0.92 ms/次 |
| 代码量 | `open_big_view` 闭包约 1000 行（与主窗口耦合） | 1400 行独立模块，只通过 1 个回调 `write_back` 与 Tk 交互 |
| 依赖 | 无 | wheel 78.1 MB / 解包 204.6 MB（打包体积大头） |

**这次试点证明的事**：
1. 同进程 Tk + Qt 共存是可行的，不需要把整个程序换成 Qt 就能拿到 Qt 的原生圆角/阴影/动画；
2. 一个窗口的迁移成本可控（独立模块 + 单回调接口），比"整体换栈"风险低得多；
3. Qt 的**暖启动 100 ms vs Tk 每次 500 ms** 是真实收益：反复开清单的场景体感差别明显；
4. 首次 953 ms 是 Qt 的一次性初始化（`setModel` 378 ms 最贵），把它藏进预热反而总耗时更长，
   所以现阶段就让它落在"第一次打开"这一次上。

**踩到的坑（已修）**：第一版为了"圆角+投影"把窗口做成 `FramelessWindowHint` + `WA_TranslucentBackground`，
结果 Qt 会给它加 `WS_EX_LAYERED` —— **DWM 对 layered 窗口直接跳过自己的弹出/关闭/最小化动画**，
用户看到的就是"窗口啪一下出现、啪一下没了"。抓屏幕帧实测（同一份内容两个窗口，开窗后逐帧与稳定帧
的差异像素占比）：

```
原生框   ： 0ms 17.0% → 67ms 8.9% → 137ms 3.2% → 192ms 0%   （约 190ms 渐变 = 系统动画在跑）
无边框半透明： 0ms 67.8% → 67ms 0% → 之后全 0%             （硬切，没有动画）
```

改回**原生窗口框**（`WS_EX_LAYERED=0`、`ex_style=0x100`）后：系统动画回来了，圆角和深色标题栏
改用 DWM 属性（`helpers.style_window_hwnd()`，Tk 与 Qt 共用同一套），顺带白拿原生阴影、四边拖拽
缩放、Win+方向键贴靠、任务栏右键菜单。代价只是标题栏由系统绘制（和 Tk 窗口长得一样，反而更统一）。

**踩到的坑二（已修）：Qt 的 `exec()` 会把 Tk 主界面整块冻住。**
本项目的 Qt 事件是靠 Tk 的 `after` 回调推的（`pump()` → `processEvents`），而 `exec()`
会开一个**嵌套事件循环**：那个 `after` 一直回不来，Tk 的 mainloop 就停在那儿。实测详情窗
`exec()` 549ms 期间 **Tk 心跳 0 次**（主界面完全不响应）。所以详情窗、确认框、提示框、
选文件框、右键菜单全部改成 `open()` / `show()` / `popup()` + 信号回调，**一次 `exec()` 都不用**：

```
改之前：模态 exec() 549ms  →  Tk 心跳 0 次
改之后：非模态详情窗 700ms →  Tk 心跳 34 次（20ms 一跳，该有多少就有多少）
        确认框 500ms → 24 次；选文件框 600ms → 27 次
```

双击最终定案（比上面这段更晚）：**用 Qt 自己的 `doubleClicked`**，程序不再按间隔自己判。
早先不用的理由是"第二次点击时会再补一发 `clicked`，和单击的选中打架"，实测（真实鼠标事件）
Qt 只发 `clicked` → `doubleClicked`，第二下**不会**再补 `clicked`；即便补了，双击回调里
"瞬间恢复原选中态 + 吃掉紧随其后的那次 clicked"也能兜住。间隔在 `ensure_app()` 里
`setDoubleClickInterval(DOUBLE_CLICK_MS)`：从 1500ms 一路往下试到现在的 **175ms**（用户按
手感定）。中途实测：1500ms 下 0.20/0.80/1.20/1.45s 两下都判成双击、1.80s 正确地算两次单击
（选中态一来一回、净变化 0），但用户觉得"间隙大了"；800ms 下 0.75s 还算双击、0.90s 已是
两次单击；150ms 下 0.10s 算双击、0.15s 已是两次单击。详情/选中都不依赖双击，右键菜单里都有。
Tk 侧对应 `<Double-Button-1>`，
间隔就是系统双击速度（0.50s），改系统值实测不生效，手慢的用户走右键菜单「详情」。

**踩到的坑三（已修）：两处"照抄 Tk 版参数"直接照抄错了。**

1. **双击间隔曾经用过 0.18s**（Tk 版 `card_list` 里那个为"快速连点不同行选中"压小的值）。
   正常人双击间隔就是 200~300ms，照抄过来等于**正常速度的双击全部失效** —— 表现出来就是
   "双击了没反应，只看到选中被切了两下"。中间试过 `helpers.system_double_click_sec()`
   （`user32.GetDoubleClickTime()`，本机 500ms，还加过 0.7s 下限）和一堆自适应方案，
   最后全部删掉，改走框架自带事件（见上）。
2. **以为 `ScrollPerPixel` 就等于平滑滚动**。它只是把滚动单位从"行"换成"像素"，滚轮还是一次跳到位。
   把 Tk 版 `SmoothScroller` 的手感搬过来（`_SmoothWheel`：每帧追剩余距离 30%、差 0.6px 吸附收工，
   连续滚轮只累加目标），表格一格 = 3 行（78px）、卡片一格 = 1 张（104px）。

**踩到的坑四（已修）：Qt 动画不能用比泵更快的时钟 + 给 QTableView 设 QSS 会毁掉滚动性能。**

先量清楚泵的能力：Tk `after(12)` 实际是 **62.7 次/秒、间隔 16.16ms**（Tk 定时器粒度约 16ms，
`after(6)` 反而掉到 26.7 次/秒，所以 12ms 已经是上限）。第一版滚动动画自己跑 12ms 的 QTimer，
**比泵还快 → 两次 tick 之间才画一帧，帧被吞、相位漂移**，看着就是掉帧。改成 `pump()` 每进来一次
推进一步（缓动系数按真实经过时间换算 `1-(1-0.3)^(dt/12ms)`），一个泵帧正好一帧画面。

改完再量，卡片已经是 65 帧/秒、帧间隔 15~16ms，但**表格还是只有 ~20fps**。把泵拆开量：

```
tick_scroll（动画本身）       平均 0.06ms   最大 0.31ms   ← 可以忽略
processEvents 表格            平均 2.61ms   最大 32.44ms   ← 瓶颈
processEvents 卡片            平均 0.29ms   最大 1.02ms
```

逐帧打印后确认：表格滚动时**每次重绘 33~43ms**。A/B 一测就清楚了 —— 是给视图设了 QSS：

```
① 视图 QSS + 表头 QSS（原来）   中位 35.38ms
② 去掉视图 QSS（表头 QSS 保留）   中位  5.23ms   ← 快 6.8 倍
③ 视图和表头 QSS 都去掉          中位  5.08ms
④ 只保留表头 QSS               中位  5.62ms
⑤ 恢复视图 QSS（回到①）          中位 34.55ms
```

**给 `QTableView` 设样式表后，Qt 就用不了"位图滚动"（blit 已画好的视口、只补新露出的那条）
快路径，每滚一步整块重绘。** 改成调色板配色（`QPalette.Base/Text/Highlight`）+ 表头单独设 QSS
（表头的 QSS 只贵 0.4ms，安全）。顺手把 `verticalHeader` 设成 `Fixed`（否则每次都要逐行问
`sizeHintForRow` 才能算滚动范围）、行底色按状态组合缓存、开窗时把两张视图 `grab()` 一次预热首帧。
改完表格滚动的帧间隔是 15~20ms（约 55~65 帧/秒），paint 从 35ms 降到 4.8ms。

**要不要继续推**：值得，但按窗口逐个来 —— 下一个候选是"模组详情/差异窗口"（纯展示+按钮，
迁移成本最低）。若继续，打包体积要重新评估（PyInstaller 侧 PySide6 一般能裁到 60~90 MB）。

### 2.9 "启动好卡，有没有库能用" —— 结论：**换库不解决，换进程才解决**

先量清楚卡在哪。启动动画（闪屏）一帧的绘制成本其实很便宜：

```
Tk+PIL 版：稳态 5ms/帧（优化后）      Qt 版（QPainter 矢量重画同一套视觉）：3.83ms/帧
```

真正的瓶颈是**主线程什么时候肯让出一帧**。构建主界面期间唯一能推进闪屏的时机是
`on_stage` 回调，实测那 1.2 秒里：

```
on_stage 只被调用 30 次，相邻间隔 [231, 67, 325, 35, 15, 24, 31, 58, 81, 42, ...]
最大间隔 325ms  ← 这段时间闪屏是完全静止的
构建期间闪屏实际只有 ~25fps
```

所以 Tk 换 Qt 没用：两个窗口在同一个主线程上，`processEvents` 还是只在 `on_stage` 时被调用。
**把闪屏放到独立进程**才有用——它有自己的事件循环：

| | 进程内 Tk 闪屏 | 独立进程 Qt 闪屏（`ui/splash_qt.py`） |
|---|---|---|
| 主线程连续忙 1.95s 时的帧率 | 25fps，最大冻结 325ms | **59.5 / 62.5 fps**（实测汇报值） |
| 闪屏出现时间 | 1.36 / 1.57s | 1.41 / 1.16s |
| 主窗口显形 | 2.76 / 3.13s | 2.89 / 2.97s |
| 额外依赖 | 无 | PySide6（已作为可选依赖；没有就回落） |

代价与坑（都已处理）：子进程启动约 0.4s，所以把它提到 emoji 预热之前并行起来（启动总耗时
因此没变）；父进程若异常退出，子进程靠 stdin EOF 立即退出不留孤儿（实测：父进程被杀后
5 秒内进程数回到基线）；拿不到 READY 就回落到进程内 Tk 闪屏。

顺手做掉的渲染优化（对进程内 Tk 版同样有效）：卡片与立方体拆成两个画布图元；立方体只上传
"卡片同位置那块 + 立方体"的**不透明补丁**（同样 210×210：半透明上传 5.66ms → 不透明补丁
0.29ms，Tk 对半透明像素走逐像素慢路径）；卡片加一份 1 倍母版、缩放没变就跳过 `SetWindowRgn`。
Tk 版稳态因此从 16.6ms/帧降到 5ms/帧。

### 2.8 顺带修掉的一个老问题：Modrinth 取版本号要等半分钟

给放大查看做联网搜索时发现的：`GET /project/{id}/version` 不带参数会把该项目**全部**版本一次拉回来，
JEI 这种版本极多的项目是 **6.58MB / 53.9 秒**，界面上就是"版本/下载链接加载中…"卡半分钟。
加一个 `?limit=1` 就够了（该接口默认按 `date_published` 倒序，第一条就是最新）：

```
不带参数： 6.58MB  53894ms
?limit=1： 0.008MB   823ms   ← 快 65 倍，版本号与文件链接完全一致
```

改的是 `core/mod_search.py` 的 `MODRINTH_VERSIONS` 常量，**Tk 版详情窗口一起受益**。
改完放大查看的联网搜索：搜索 1.0s 出结果、版本号 1.8s 内全部填好（原来要 50 秒以上）。
