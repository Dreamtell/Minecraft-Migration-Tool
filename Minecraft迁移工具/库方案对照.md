# 手写部分 vs 现成库：对照清单

> 目的：遇到棘手问题时，先看有没有库能省事，而不是一律手写。
> 本文只做评估，不改代码。所有"本地实测"数字都是在当前代码上量的。

## 0. 结论速览

| 手写的东西 | 规模 | 有无库可替 | 结论 |
|---|---|---|---|
| `VirtualTable` 自绘表格 | 510 行，**只有 1 处调用** | `tksheet` 7.6.0（已装） | **实测后不建议换**（见 2.1：换上去滚动会变卡） |
| 手写系统托盘 `tray.py` | 191 行，6 处引用 | **`pystray`**（已装 0.19.5） | 可换，但注意 LGPLv3 |
| 无原生暗色标题栏 / 窗口圆角 | 0 行（缺功能） | **`pywinstyles` 1.8** | **已采用**（CC0，50KB，打包零风险） |
| ttk 控件主题（Treeview/Entry/滚动条…） | `theme.py` 156 行 + 各窗口手写补色 | `sv-ttk` / `ttkbootstrap` | **不换**（管不到自绘控件，且 sv-ttk 有打包坑） |
| 圆角渐变按钮 / 手绘图标 / 平滑滚动 | `helpers.py` 638 行，53 处调用 | `CustomTkinter` 6.0.0（**已实测**） | **不换**（见 2.6：它的按钮内部也是 canvas+label，换上去只是换封装） |
| 启动动画 | `splash.py` 405 行 | 无（Tk 内） | 不换 |
| 单控件淡入淡出、布局动画 | — | 只有换栈（PySide6） | 现在不换，等整套视觉改版 |

## 2. 逐个看

### 2.1 `tksheet` 替 `VirtualTable` —— 做过并排 demo，**实测结论：不换**

- 现状：自绘 Canvas 表格 510 行，自己管可见行、槽位复用、排序、悬停、水平滚动、平滑滚动。
- 库：[tksheet](https://pypi.org/project/tksheet/) 7.6.0，MIT、2.5 MB、零依赖。
- 并排 demo（同一份 500 行数据、都用深色主题，截图 `表格对比demo.png`）实测：

| 项目 | 旧：VirtualTable | 新：tksheet 7.6.0 |
|---|---|---|
| 构建 500 行 | 590 ms | **301 ms**（快一倍） |
| 滚轮一格 | 平滑动画，7 帧 / 132 ms，单帧重绘 **0.03~4 ms** | **一次跳到位**（无动画），单次重绘 **23~38 ms**（800 行与 2000 行都是 ~24 ms） |
| 附带功能 | 无 | 行号列、列宽拖拽、点表头排序、复制、查找、单元格编辑、下拉 |
| 配色 | 就是我们的主题（含 ✅/❌/⚠️ tag 色） | 它自带深色主题，另一套色板；要贴合得逐项喂色 |
| 已接好的东西 | 主题同步、悬停提示、拖拽 .jar、勾选语义、平滑滚动 | 全都要重写 |

- **否决理由**：滚动重绘贵 6~10 倍（24 ms vs 4 ms）。我们刚做完的平滑滚动是"每帧插值"的，单帧 24 ms 已经超过 60fps 预算（16.7 ms），换上去等于**用卡顿换少写 510 行**——而这 510 行的功能已经全都接好了。
- 什么情况下值得回头再考虑：如果哪天要**单元格编辑、列宽拖拽、搜索、多列排序**这些它白送的功能，那时可以把"放弃平滑滚动"当作可接受的代价。
- 待验证（本机网络受限，pip 拿不到包）：PyInstaller 是否需要 `--add-data`。

### 2.2 `pystray` 替手写托盘 —— 可换，注意许可

已在本机**验真**（它已经装在环境里）：

```
版本 0.19.5   许可 LGPLv3   安装体积 257 KB / 35 文件
依赖 Pillow + six（+ 各平台各自的包）
Icon 方法：run / run_detached / notify / update_menu / stop
MenuItem(text, action, checked, radio, default, visible, enabled)   ← 勾选项、单选、左键默认动作都支持
后端：pystray/_win32.py
```

- 它能覆盖我们现在手写的：勾选式菜单项（"关闭时收进托盘"）、左键打开主界面、气泡通知。
- **它不覆盖**：再次双击 exe 时唤起已有实例、把窗口从托盘叫回来——那套 `RegisterWindowMessage` 逻辑仍要保留（这部分是本项目特有需求，不是托盘的锅）。
- **许可要注意**：LGPLv3 打进 PyInstaller 单文件 exe 属于合规灰区（常见做法是随包附源码或允许替换库）。我们现在的 `pywin32` 方案没有这个问题。

### 2.3 `pywinstyles`（原生暗色标题栏 / 圆角）—— 建议加

- 现状：深色主题下窗口标题栏仍是白色（Tk 不管标题栏）；窗口四角是直角。
- [pywinstyles](https://socket.dev/pypi/package/pywinstyles/overview/1.8) 用 ctypes 调 DWM：暗色标题栏、圆角、亚克力/云母、标题栏配色。
- 纯 ctypes、无数据文件 → PyInstaller 打包基本无风险（对比 sv-ttk 的 `.tcl` 坑）。
- 代价：一处调用（应用主题时给主窗口 + 各 Toplevel 刷一次），几行代码。
- 待验证：Win10 上的降级行为、部分窗口（overrideredirect 的提示框）是否要跳过、许可。

### 2.4 `sv-ttk` / `ttkbootstrap`（ttk 主题）—— 不换

- 它们能把 ttk 控件（Treeview、Entry、Combobox、Scrollbar、Progressbar）一键换成 Win11 风格。
- 但本项目**所有主要控件都是自绘**（53 处渐变按钮、自绘表格、自绘启动卡片），它管不到；剩下那几个 ttk 控件我们已按主题逐个配过。
- 另外 [sv-ttk 有已知 PyInstaller 打包问题](https://github.com/rdbende/Sun-Valley-ttk-theme/issues/86)（`sv.tcl` 要 `--add-data`，否则报 `couldn't read file ...sv_ttk\sv.tcl`）。收益小、坑不少。

### 2.5 `PySide6`（换栈）—— 现在不做

只有它能解决 Tk 架构上做不到的两件事：单控件淡入淡出（`QGraphicsOpacityEffect`）、布局动画（`QPropertyAnimation`）。代价：`ui/` 4000+ 行重写、打包体积 +50~80MB、托盘/通知/拖拽全换实现。等整套视觉改版时一次性做。

### 2.6 `CustomTkinter`（"专门做现代化美化"的那个库）—— 实测后**不换**

问题原话是"为什么就没有专门搞现代化设计美化的库呢"。有，就是它：[CustomTkinter](https://pypi.org/project/customtkinter/)，
MIT，纯 Python，自带深/浅色与多套配色主题。**本次已在本机装上并实测**（pip 的临时目录被沙箱拦了，
改用 urllib 直接下 wheel + zipfile 解包）：

```
customtkinter 6.0.0 wheel 295 KB + darkdetect 0.8.0 9 KB + packaging 127 KB = 431 KB
随包数据文件 8 个：assets/fonts/CustomTkinter_shapes_font.otf、assets/fonts/Roboto/*.ttf、
                  assets/icons/*.ico、assets/themes/*.json（blue/dark-blue/green/gold…）
```

实测数据（同一台机器，本机噪声大，比值比绝对值可信）：

| 项目 | CustomTkinter 6.0.0 | 本项目现状 |
|---|---|---|
| 导入耗时 | **387 ms** | tkinter 约 50 ms |
| 按钮构建 | 4.89 ms/个（12 个 59 ms） | 0.4 ms/个（渐变图缓存命中） |
| 输入框构建 | **14.88 ms/个**（3 个 45 ms） | 0.27 ms/个 + 4 ms 懒出图 |
| 200 行滚动列表构建 | 123 ms（0.62 ms/行，200 个真控件） | 卡片视图按需只画可见 12 行 |
| 滚动一屏 | 2.2 ms 中位 | 9.6 ms/帧（但我们是逐帧插值动画，不是整块跳） |
| 首次绘制（demo 窗口） | 852 ms | 主窗口（大得多）1120–1279 ms |
| 默认字体 | **Roboto**（自带 TTF） | 全程序微软雅黑 |
| 打包 | 8 个 .otf/.ttf/.json 要 `--add-data`（同 sv-ttk 那类坑） | 纯代码 + Pillow，无数据文件 |

**它为什么不是魔法**（这是本题的关键）：实测 `CTkButton` 的子控件是 `[CTkCanvas, Label]` ——
跟我们手写的渐变按钮是同一套路（Canvas 上贴图/画形状 + 文字）；`CTkEntry` 也是 canvas 包一个原生
`Entry`，和我们刚做的 `RoundedEntry` 一模一样。也就是说 Tk 生态里所有"美化库"最后都只能：
**在 Canvas 上自己画像素，再把原生控件嵌进去**。谁来做都绕不开，区别只是封装程度。

根因是 Tk 的三条硬限制：
1. 控件没有 `border-radius`，ttk 的 style 只能替换**预定义绘制元素**，不能定义新形状；
2. 没有"单控件 alpha"和控件级合成，全窗口只有 `-alpha`（还是 layered window，会挡掉系统动画）→ 做不出阴影/毛玻璃；
3. Tk 的核心从 8.6 到 9.0 基本没动过样式层；而 Tk 的用户群是脚本/小工具，没人投钱做设计系统（对比 Qt 有 Qt Company、Flutter/Electron 有大社区）。

**结论：不换。** 换上去的收益是"少写自绘代码"，代价是：
- 现在 4000+ 行 UI（窗口/表格/卡片/动画/主题）全要重写；
- 丢掉已经调好的东西：像素级平滑滚动、卡片视图、自绘表格（CTk 没表格，要另配 tksheet，而 tksheet 滚动 23–38 ms，见 2.1）；
- 丢掉主题统一：它自带一套 JSON 主题 + Roboto 字体，我们这边 130+ 语义色键、几十处引用都对不上；
- 打包多 8 个数据文件、多 431 KB 依赖，外加一个第三方维护节奏（6.0.0 之后更新已明显放慢）。

真要做"整套现代化"，一步到位应该上 **PySide6 + qfluentwidgets**（Windows 11 Fluent 质感、真圆角阴影、QSS 样式表、原生动画），而不是在 Tk 上再包一层。

## 3. 建议顺序

1. **`pywinstyles`**：小、独立、收益肉眼可见（暗色标题栏 + 原生圆角），先做这个验证"引库"这条路顺不顺。
2. **`tksheet` 替换 `VirtualTable`**：只有 1 处调用，删 510 行自绘代码；需要先允许联网装包，验证打包与中文。
3. `pystray`：可选，除非你觉得现有托盘不稳；注意 LGPLv3。
