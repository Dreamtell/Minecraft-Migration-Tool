# Tk 主进程性能笔记（本项目实测版）

> 这份**只讲这个项目**：Tk 主进程 + PySide6 子进程的 Windows 桌面工具。
> 通用库速查表见 `perf-notes.md`；通用清单里哪些能用、哪些别碰，见文末「通用清单裁决」。
> 所有数字都是在开发机上实测的（探针见 `_dctest/probe_*.py`）。

## 0. 一句话结论

**这个项目的卡顿从来不是"少装了一个库"，而是五件事：**
事件循环被灌爆、`update_idletasks` 打得太勤、每帧重烤位图、Tk 定时器精度、
以及**动画期间忘了 `anim.hold()`（这条最隐蔽，见 §4）**。
先把这几条按顺序排掉，比换任何框架都管用。

## 1. 事件循环洪水（最致命）

**症状**：迁移时主窗口标题变成「(未响应)」，卡几秒到二十几秒。

**根因**：迁移线程每产生一行日志就 `root.after(0, 写这一行)`。
1500 行 = 1500 个回调 + 每个回调里一次 `configure/insert/see` + 一次淡入动画。
看门狗抓到过 **21.45 秒**的主线程栈：全部停在 `update_idletasks ← _log ← _ui_pump`。

**修法**（提交 218ee49 / 59fd3da / b34458a / 6e76c68 / 9f4000c）：

- 主线程日志改成「先进队列、50ms 合并写一次」，一次最多 24 行；
- worker → 主线程的泵加预算：`_UI_PUMP_MAX_ITEMS = 60`、`_UI_PUMP_BUDGET_MS = 10.0`；
- 日志整批写（`_日志批次开始/结束`）时**不要**每行 `update_idletasks`；
- 跟随滚动（`see`）与修剪行数拆开，各自节流（80ms / 150ms）。

**实测**：主线程连写 1500 行 0.84s → **0.11s**；单次最长 290ms → **20ms**。

## 2. `update_idletasks()` 不要放在逐条回调里

**症状**：进度窗口看得见在动，但像 10fps；迁移一结束又"卡一下"。

**根因**：`ProgressWindow.update_progress()` 末尾每条都 `update_idletasks()`（注释写了"要节流"但代码没有），
1000 个文件 = 1000 次全量重绘，单次能卡 1 秒以上。

**修法**（提交 5b9a34a）：

- 节流到 100ms；
- 进度条自己 `_tick` 里对**这块画布**限频 40ms；
- `LiquidProgress._TICK_MS` 从写死 33 改成跟刷新率（`anim.frame_ms()`，夹 4~16ms）；
- `set_fraction` 的变化阈值 0.002（500px 条 = 1px，不足 1px 的推进被丢掉）→ 0.0005。

**实测**：`itemconfig(image=)` 45.6 → **151.6 次/秒**，间隔 p50 16.3 → **7.9ms**。

## 3. 自绘控件：别每帧重烤位图

**症状**：翻转按钮背面"迁移中"那屏明显掉帧。

**根因**（提交 85686f3）：底部进度条被合进"整张脸"里，脸每帧换相位就要重新合成
（底 + 斜纹 + 条 ≈ 4.5ms/帧），正好锁死在 30fps。

**修法**：

- 条拆成**独立画布项**（`_bar_id`），只 crop 已经烤好的满宽条；
- 缓存键要带**所有**影响像素的参数（颜色、悬停档、相位…），漏一个就会出现"改了没反应"；
- 相位表 72 → 180 是"够用且不亏"的档：试过 300，每帧多烤整面，单帧涨到 2.2ms、
  间隔反落到 10.2ms、条只变 76 次/秒 —— **退回 180**。

**实测**：画面真变化 25.2 → **72.7 次/秒**，间隔中位数 33.6 → **15.4ms**。

## 4. Tk 的定时器精度：`after(4ms)` ≠ 4ms

**症状**：想把动画拉到 144Hz，结果一直卡在 60~64 次/秒。

**根因**（提交 d5159b9 / 1b3adc9）：Windows 上 Tk 的 `after` 默认被系统 15.6ms 粒度拉回；
只有"需要高精度"时才 `timeBeginPeriod`（我们封装成 `anim.hold/release`）。
原代码**只在正面** hold，背面（一直有斜纹和条在动）没 hold —— 于是背面只跑到 30~64fps。

**修法**：

- tick 一律 `hold_hr()`、停表一律 `release_hr()`；
- `_tick_ms()` 一律跟刷新率（夹 `_TABLE_MS_MIN.._UI_MS`），不要给"没进度就退回 33ms"的分支；
- 条按 1/4 像素量化（`_BAR_SUBPX = 4`），否则一帧该走 0.3px 却被量化成整像素，看着一顿一顿。

**实测**：条 61.3 → **95~99 次/秒**，间隔 p50 16.1 → **8.5ms**；
单帧 `_ui_tick` p50 0.59ms / p90 2.34ms。要真吃满 143Hz，得整区重绘或搬到 Qt 侧。

### 4.1 封装：`anim.FrameLoop`（提交 b06aa61）

"忘了 hold"这个坑我们**踩了三次**（消息中心滚动、吐司、日志跟随），表现都是
"看着能跑、其实卡在 64fps"。第三次之后把它封成机制：

```python
环 = anim.FrameLoop(widget, 每帧函数, slow=False)   # 每帧函数返回 False 即结束
环.start()    # 内部 hold()，按 delay(widget) 排期
环.stop()     # 随时可停：after_cancel + release()
```

- `step()` 返回 False 或**抛异常** → 自动 `release()`，不会留下"精度被顶住但没人还"；
- `slow=True` 固定 30fps（拖浮标这类要让路的场景）；
- 重复 `start()` 不会重复 hold；`running()` / `帧数` 供探针读。

### 4.2 这一轮的实际收益（本机 142.9Hz）

| 位置 | 改前 | 改后 | 提交 |
|---|---|---|---|
| 吐司动画 | ~62 次/秒（16ms） | **95 次/秒**，p50 10.5ms | b1297a8 |
| 日志跟随滚动 | ~64 次/秒（被 15.6ms 卡住） | **~124 次/秒**（112 次采样 / 56 个位置） | 3d62efb |
| 消息中心滚动 | 一格一跳 | 一格摊 **~12 帧 / 100ms**，单帧最大跳 0.009 | b1297a8 / b06aa61 |
| 翻转按钮文案淡入 | 每档 18ms，一跳一跳 | 按帧摊，5 档 / **76ms** | 08cb8a7 |
| 延迟曲线图 | 8ms 目标但没 hold | 循环起始 hold，关闭时 release | b1297a8 |

**注意**：翻转按钮背面 `anim.holding()` 长期是 True 是**应然**——背面斜纹和进度条
一直在动，tick 需要高精度定时器；翻回正面并停下后应回到 False（探针里断言这一点）。

## 5. GIL 争用：worker 里干的活也会拖住 UI

**案例**：`core/migrator.py` 的 `remove_old_mod_versions` 用 `zipfile` 逐个读 jar 取 modid。
430 个 jar 实测 **1.31 秒**（平均 2.97ms/个，超 200ms 的阻塞 0 次）——
**不足以**造成 700ms 卡顿，但确实会周期性抢 GIL。

**结论**：先量再改。真要优化，方向是缓存/批量解析（已有 `_MODID_CACHE`），不是"加个线程池"。

## 6. 测量方法（都是踩过坑才定下来的）

| 要测什么 | 怎么测 | 坑 |
|---|---|---|
| 主线程有没有被堵 | 主线程 `after(1)` 心跳 + 记录相邻间隔最大值 | 拿 UI 线程自己的栈看不到别人堵它 |
| 卡在哪 | `utils/hangwatch.py`（独立线程 + `faulthandler.dump_traceback`，阈值 0.4s） | 在主线程回调里 dump 只能抓到自己 |
| 动画帧率 | 在探针里按固定间隔读状态（`btn._bar_u()`），或数"贴图真的换了"的次数 | 钩渲染函数会被重复调用污染，得到假的"没变化"比例 |
| 像素是否真变 | 抓帧后逐像素比，注意按 DPI 换算裁剪框 | 每帧必须先 `update()` 再 `ImageGrab`，否则抓到重复帧 |

## 7. 铁律清单

1. **帧率只调排帧间隔，速度必须按 `perf_counter` 的真实 dt 算**（否则改帧率 = 改速度）。
2. **worker 线程绝不直接碰 Tk**：一律 `_ui_post`，主线程泵里带预算地执行。
3. **批量写日志**：一次 `update` 写完一批，比一千次小更新快一个数量级。
4. **缓存键要包含所有影响像素的输入**（主题、颜色、悬停档、相位、DPI）。
5. **自绘控件的"重画"往往不止一个方法**：文字是画布 item 时，光调 `_redraw()` 只换底图不换字。
6. **先剖析再动手**：`cProfile` 一次比自己猜十次准。
7. **动画一律用 `anim.FrameLoop`**：它替你 hold/release 定时器精度与异常收尾；
   手写 `after()` 循环时，别忘了 `anim.hold()` 并在**所有**退出路径上 `release()`。
8. **探针要先摆对初始状态**：例如抽屉打开时停在最底部，发**向下**的滚轮永远测不出位移；
   窗口不 `show()` 时 Qt 的 `isVisible()` 恒为 False。

## 8. 通用清单裁决（对照 `perf-notes` 那份 Tkinter 清单）

| 清单里的建议 | 本项目裁决 | 理由 |
|---|---|---|
| `threadom` | 用不上 | 等价于我们已有的「子线程 + 队列 + 主线程泵」，且我们的版本带预算与优先级 |
| `async-tkinter-loop` / `Cengal` / `Tkinter-Async-Execute` | 不建议 | 会把第二个事件循环塞进 Tk，和 `after` 帧预算互相抢；Tk 非线程安全的坑一个没少 |
| `tkfastscatter` / `anytk3d` | 用不上 | 我们是 2D 折线 + 表格；大视图已经整体在 PySide6 子进程 |
| 延迟导入耗时库 | 已在做 | `matplotlib` 只在打开曲线图时 import（180ms / pyplot 302ms）；Qt 只在子进程；`main_window` 在 `main()` 里才 import |
| 迁 PyQt / PySide | 不建议 | 大视图已在 PySide6 子进程；全量迁移 = 维护两套 UI + 发行包多带一份 Qt |
| `ttkbootstrap` / `CustomTkinter` | 同意是伪优化 | 控件都是自绘的（渐变按钮 / 药丸页签 / 滑杆 / 翻转按钮） |

**启动导入实测**：`ui.main_window` 129ms（tkinter 22 / PIL 18 / `core.mod_search` 25），
里面没有 requests、没有 matplotlib、没有 Qt —— 启动阶段没有可压的大头。
